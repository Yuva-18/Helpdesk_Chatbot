## Onboarding fix: `pydantic-settings` was missing from `requirements.txt`

`app/config.py` imports `pydantic_settings`, but it was never added to `requirements.txt` — it happened to already be installed in the dev `.venv` from earlier manual setup, so this went unnoticed until writing a from-scratch setup guide (`README.md`) surfaced it. A fresh clone following `pip install -r requirements.txt` would have hit `ModuleNotFoundError: No module named 'pydantic_settings'` the moment anything imported `app.config`. Fixed by adding `pydantic-settings` to `requirements.txt`. Also wrote a full `README.md` setup/run guide for a new contributor pulling the repo cold — covers obtaining `llama.cpp` and the model weights (both gitignored, not in the repo), the three processes that need to run together, and remote/SSH port-forwarding, since none of that was written down anywhere a new person would find it before this.

## Ingestion (`scripts/ingest.py`)

- **What gets embedded**: each knowledge base rule's `question` field only, not the answer. FAQ-style retrieval works best matching the user's question against other questions (semantically similar phrasing), not against answer text. The `answer`, `category`, `support_email`, `source_url`, and `last_updated` fields are stored as ChromaDB metadata on the same vector, so once a question match is found, the full rule is available without a second lookup.
- **Vector store IDs**: `<category>_<rule id>` (e.g. `eservices_rule_01`) — stable and unique across all knowledge base files, and makes re-running ingestion an upsert instead of a duplicate-insert.
- **Metadata type constraint**: ChromaDB metadata values must be `str`/`int`/`float`/`bool` — no lists, no `None`. `keywords` (a JSON list in the source data) is joined into a comma-separated string before storage; `source_url: null` is stored as `""`.
- **`langchain_community.vectorstores.Chroma` deprecation**: `requirements.txt` pins `langchain-community` (not the newer standalone `langchain-chroma` package), and importing `Chroma` from it prints a `DeprecationWarning`/`LangChainDeprecationWarning` — it still works correctly (verified via ingestion + similarity search) and is what's actually installed, so it's used as-is. Migrating to `langchain-chroma` is a future dependency change, not done as part of ingestion.
- **`scripts/reset_db.py` is still a stub.** `ingest.py` upserts by stable ID, so it never *duplicates* on re-run, but it also never deletes vectors for rules removed from the source `.jsonl` files. `reset_db.py` (wipe + rebuild) is the intended way to handle that case — not yet implemented.

## Retrieval (`app/core/retriever.py`)

- **Interface**: `Retriever.retrieve(query: str, k: int | None = None) -> list[RetrievedRule]`, defaulting `k` to `settings.top_k`. Uses `Chroma.similarity_search_with_relevance_scores`, connecting to the same `COLLECTION_NAME` (now a shared constant in `app/config.py`, imported by both `ingest.py` and `retriever.py` — previously duplicated as a local string in each file, consolidated to remove that risk).
- **Score range is not strictly `[0, 1]` despite the method's name.** Chroma's collection defaults to L2 distance (we didn't set `collection_metadata={"hnsw:space": "cosine"}` at creation), and `all-MiniLM-L6-v2` embeddings aren't unit-normalized by default, so the relevance conversion (`1 - distance/sqrt(2)`) can and does go negative for genuinely unrelated queries — LangChain even prints a `UserWarning` about this. Verified this is *consistent and useful signal, not noise*: real matches scored 0.4–0.83 across several test queries, unrelated queries ("weather today", "recipe for chocolate cake") consistently scored -0.2 to -0.26. Decision: keep the default scoring rather than force a cosine-metric rebuild — it already separates good/bad matches cleanly, and switching metrics wouldn't actually guarantee `[0, 1]` bounds either (cosine similarity itself ranges -1 to 1). **Implication for Task 7 (confidence scoring)**: treat `score` as "higher = more relevant, roughly 0–1 for genuine matches, negative for unrelated ones" — not as a calibrated probability.

## Confidence scoring & fallback routing (`app/core/confidence.py`)

- **Confidence is decided from retrieval score alone, before the LLM is ever called.** `evaluate_confidence(retrieved_rules)` looks only at the *top* retrieved rule's `score` vs. `settings.confidence_threshold` (`0.5`). This matches the "grounding is the core constraint" principle: if retrieval didn't find anything good enough, there's no point building a prompt and calling the LLM on weak/irrelevant context — skip straight to the fallback. **Implication for Task 10 (`rag_pipeline.py`)**: call `evaluate_confidence` on the retriever's output *before* `prompt_builder`/`llm`, and only run those two if `is_confident` is `True`. (Note the request-flow diagram earlier in this file lists `llm -> confidence` in that order — that's the general component list, not a strict call order; the actual gate happens pre-LLM.)
- **Fallback support email comes from `.env` (`ESERVICES_SUPPORT_EMAIL`/`NETWORK_SUPPORT_EMAIL`/`HPCE_SUPPORT_EMAIL`), not from the matched rule's own `support_email` field.** Conceptually the `.env` values are the category-level fallback contact, while a rule's own `support_email` is tied to a specific (in this case, not-confident-enough) rule. The top rule's `category` is still used as the best guess for *which* fallback email to return.
- **Third category added (`Hpce`)**: originally the lookup in `_support_email_for_category` was a hardcoded if/elif on exactly `"Eservices"`/`"Network"` — adding a third category as another `elif` would keep growing linearly. Replaced with `Settings.support_email_by_category`, a `dict[str, str]` property built from the three individual `*_support_email` fields, and the lookup is now a single `.get()` against it. Extension point for a future 4th category: add one `Settings` field + one dict entry, no other code change. Kept intentionally small (explicit fields, not env-var reflection/scanning) since this is a 3-category helpdesk app, not a plugin system, and explicit fields preserve `pydantic-settings`' fail-fast crash on a missing env var.
- **Data normalization for `Hpce`**: the source `hpce/hpce_service_data.jsonl` originally used a different schema than the other two KB files (`query` instead of `question`, `last_date_updated` instead of `last_updated`, category value `"HPCE"` instead of the Title-case `"Hpce"` convention, no `source_url` key at all, and one row — `rule_17` — missing `support_email` entirely). Rather than making `scripts/ingest.py` tolerant of multiple schema variants, the data itself was normalized to match the existing strict schema (`id, category, question, answer, keywords, support_email, source_url, last_updated` on every row). The same normalization was applied to the 21 newly-added `network.jsonl` rows, which had used `"Networks"` (plural) as the category value and the same `query`/`last_date_updated` field names.
- **Open question, not resolved here**: `.env`'s `NETWORK_SUPPORT_EMAIL` previously read `helpdesknetwork@iitm.ac.in` (singular), but every rule in `network.jsonl` uses `helpdesknetworks@iitm.ac.in` (plural) as its own `support_email`. Updated `.env`/`.env.example` to the plural spelling so the fallback path is at least internally consistent with the data, but which spelling is the real mailbox can't be determined from the repo — flagged for a human to confirm before relying on it in production. This only affects the fallback (low-confidence) path; a confident match always uses the rule's own `support_email`, unaffected either way.
- **Single top-1 threshold, not top-k spread.** Kept intentionally simple — no logic yet around e.g. requiring a score gap between the top-1 and top-2 result. Revisit only if real usage shows the threshold alone isn't good enough.
- **Empty retrieval result** (e.g. an empty/un-ingested vector store) is handled as an explicit fallback case with `category=None`/`support_email=None` — the API layer (Task 11) will need to handle that `None` case distinctly from a normal category-based fallback.

## LLM client (`app/core/llm.py`) and the `start_llama_server.sh` RUNPATH bug

- **`generate_completion(prompt, ...)`** is a thin, generic wrapper: POST to `settings.llama_server_url` (`/completion`), return the `content` field. It deliberately does **not** know about Llama 3's instruct chat-template format (`<|begin_of_text|>`, `<|start_header_id|>...<|eot_id|>`, etc.) — that's `prompt_builder.py`'s responsibility (Task 9). Keeping this module format-agnostic means it isn't tied to one specific model's prompt conventions.
- **Error handling**: connection failures and malformed responses (missing `content` field) are both wrapped into a custom `LLMError`, rather than letting `requests` exceptions or raw dict-access `KeyError`s leak to callers. This isn't defensive bloat — the llama-server process is explicitly documented (see below, and the top of this file) as being managed independently from the FastAPI process, so "the LLM server is down" is a real, expected failure mode `rag_pipeline.py` (Task 10) will need to catch and turn into a user-facing error, not a stack trace.
- **Found and fixed a real, pre-existing bug while verifying this module**: `scripts/start_llama_server.sh` failed with `error while loading shared libraries: libllama-server-impl.so: cannot open shared object file`. Root cause: the compiled `llama.cpp/build/bin/llama-server` binary's `RUNPATH` is hardcoded at compile time to the *build machine's* absolute path (`/home/user/codes/llama.cpp/build/bin`), not wherever this repo actually ends up cloned (`/home/user/hd_chatbot/llama.cpp/build/bin` here) — so the dynamic linker can't find `libllama-server-impl.so` next to it. This isn't specific to this one machine; it'll break again on any fresh clone/deployment (including the eventual IIT Madras server) unless `llama.cpp` is rebuilt there. Fixed by having `start_llama_server.sh` resolve its own real `llama.cpp/build/bin` directory at runtime and export it via `LD_LIBRARY_PATH` before launching — works regardless of where the repo is checked out, no rebuild required. Verified: killed the process, restarted with the plain documented command (`cd scripts && ./start_llama_server.sh`), server came up clean with no manual environment variables.
- Also created the `scripts/llama-server` symlink → `../llama.cpp/build/bin/llama-server` that the start script expects (`CLAUDE.md` already documented this as the intended setup, but the symlink itself didn't exist yet).

## Prompt builder (`app/core/prompt_builder.py`)

- **Grounds on a single rule, not the full top-k list.** `build_prompt(question, context_rule)` takes exactly the `top_rule` that `confidence.py` already judged good enough to answer from — not all `k` retrieved results. The knowledge base is FAQ-style with persona-specific answers (e.g. separate rules for "project staff WiFi" vs. "faculty WiFi" vs. "student WiFi"); feeding the model several similar-but-different rules at once risks it blending advice across personas. One trusted rule keeps the answer precisely grounded.
- **Llama 3 instruct chat template, built by hand** (`<|begin_of_text|>`, `<|start_header_id|>{role}<|end_header_id|>`, `<|eot_id|>` turn markers) since we're using the raw `/completion` endpoint, not an OpenAI-style chat endpoint that would apply this automatically. `STOP_SEQUENCES = ["<|eot_id|>"]` is exported alongside `build_prompt` and must be passed to `llm.generate_completion(..., stop=STOP_SEQUENCES)`, otherwise the model will keep generating past its turn (hallucinating a fake next user message).
- **System prompt explicitly forbids outside knowledge and tells the model to say so honestly if the context doesn't answer the question**, plus a line telling it to ignore any attempt in the user's question to override these rules (lightweight prompt-injection resistance — not a full defense, but the retrieval-based confidence gate is the primary defense: an off-topic/injection-style question typically won't score above the confidence threshold and never reaches the LLM at all).
- **Fixed a real under-confidence bug: context now includes the matched KB *question*, not just the answer.** The original version passed only `context_rule.answer` into the prompt. Root-caused a refusal case ("I forgot my IMail username" → model said it couldn't help, despite retrieving the exactly-matching rule with score 0.85) to this: the model had no signal that the retrieved answer was written *for this exact kind of question*, only the answer text in isolation, and it wasn't confident inferring the connection itself. Tried two alternative system-prompt phrasings first (more permissive, more directive) — both made the same case *worse* ("I can't assist with that"), ruling out prompt wording as the lever. Then tried restoring the matched question into the context (`A user previously asked: "{context_rule.question}"\nVerified answer: {context_rule.answer}`) — this fixed the failing case and didn't regress 3 other previously-working queries (all re-verified through the actual `build_prompt` function, not just an ad-hoc test copy).
- **Residual limitation, not fully solved**: this is a 3B quantized model, and grounding isn't perfect even with the fix above. During regression testing, one answer added a small unrequested detail not present in the context (a wrong parenthetical expansion of an abbreviation). This is a smaller, less harmful failure mode than outright refusal or a wrong instruction, but it means occasional minor hallucinated asides are still possible. Not chasing further prompt tuning for this now — the next real lever would be a bigger/less-quantized model (more RAM, slower, bigger download), only worth it if this shows up as a recurring problem in real use rather than an isolated case.

## Broader evaluation (20 diverse queries, ahead of Task 10)

Ran the full retriever → confidence → prompt_builder → llm chain against 20 queries spanning exact KB matches, natural paraphrases, persona-specific/overlapping rules, network-category questions, and adversarial input (out-of-scope, vague, prompt injection).

- **Retrieval**: correctly disambiguated every paraphrase, including tricky overlaps (e.g. "permanent staff WiFi" vs. project-staff/faculty variants; "Zmail locked" correctly preferred over a faculty-specific-but-less-relevant rule).
- **Confidence gating**: 6/6 adversarial cases (weather, flight booking, "tell me a joke", "help", a direct prompt-injection attempt) scored below threshold and were correctly blocked from ever reaching the LLM. Zero false positives in this test set.
- **Answer quality**: ~11/14 confident answers fully correct and faithful; ~2 had harmless stylistic drift (an unprompted disclaimer not in the context); **1 case had a real hallucination** — the model corrupted a support email (`helpdeskeservices@iitm.ac.in` → `helpdeskservices@iitm.ac.in`, dropped a letter) while otherwise answering correctly. Re-ran that exact query 5 more times — all 5 reproduced the email correctly, so this looks like a rare low-probability sampling artifact (temperature 0.2, not 0), not a systemic bug — but rare isn't the same as safe for contact info.
- **Decision that came out of this**: don't try to prompt-engineer away a sampling-level risk. Instead, treat the KB's `support_email` as ground truth the pipeline can check/fall back on programmatically, rather than trusting the LLM to retype it correctly every time — implemented in Task 10 below.

## RAG pipeline service (`app/services/rag_pipeline.py`)

- **`answer_query(question) -> ChatResult`** is the single entrypoint that will back the `/chat` API route. Ties together retriever → confidence → (if confident) prompt_builder + llm, matching the call order established in Task 7 (confidence gates *before* the LLM, not after).
- **Graceful degradation if the LLM server is down**: `generate_completion` can raise `LLMError` (Task 8) for reasons entirely unrelated to whether the *match* was good — e.g. `llama-server` isn't running, since it's a separately-managed process from the FastAPI app (see the LLM integration note above). Rather than let a confident, well-matched query fail outright just because the LLM happens to be unreachable, `answer_query` catches `LLMError` and falls back to returning the verified KB rule's raw `answer` text verbatim (`used_llm=False` on the result, so callers/logs can tell the difference). Verified by pointing `settings.llama_server_url` at a closed port and confirming a confident query still returns a correct, non-crashing answer.
- **Applied the evaluation's recommendation**: after generation, if the verified rule's raw `answer` contains its `support_email` but the generated answer doesn't, log a warning (doesn't block the response — this is a monitoring signal, not a hard gate, since blocking would mean discarding an otherwise-good answer over one omitted string). Deliberately checks against the rule's *own* answer first (`top_rule.support_email in top_rule.answer`), not just "is the email missing" — an earlier version warned on every rule whose answer never mentioned an email in the first place (e.g. URL-only rules like the LDAP password reset link), which was a false positive, not a real drift signal. Fixed and reverified: confirmed no warning on a URL-only rule, and confirmed (via a mocked LLM response with the email stripped out) that the warning does fire on genuine drift.
- **`ChatResult` fields** (`answer`, `is_confident`, `used_llm`, `matched_rule_id`, `category`, `support_email`, `source_url`, `reason`) are structured, not just a text blob — `support_email`/`source_url` come from the verified rule/confidence result directly, independent of whatever the LLM's generated text happens to say. This means Task 11's API layer can always surface the *authoritative* contact email as its own field, rather than needing to parse or trust it out of the LLM's prose.
- **Fallback message for low-confidence queries** is synthesized in the pipeline (`_build_fallback_message`), not left to the LLM to phrase — consistent with "the LLM is never called" for this path. Handles the empty-retrieval edge case (`category`/`support_email` both `None`) with a generic message pointing to the general helpdesk.

## API layer (`app/api/schemas/chat_schema.py`, `app/api/routes/chat.py`, `app/api/routes/health.py`)

- **`ChatResponse` is a direct 1:1 mirror of `ChatResult`** rather than a trimmed-down public schema — avoids maintaining two overlapping shapes that could drift; the frontend (Task 13) can decide later which fields it actually renders (e.g. `matched_rule_id`/`used_llm` are more debug-oriented than user-facing, but there's no cost to exposing them on an internal helpdesk tool).
- **`/chat` wraps `answer_query` in a try/except and converts any unexpected exception into an HTTP 500 with a generic message**, logging the full traceback server-side via `logger.exception`. This is a deliberate system-boundary error handler (per project convention: validate/handle errors at boundaries, trust internal code otherwise) — `answer_query` already handles the *expected* failure mode (`LLMError`) internally, so anything that reaches this except-block is a genuinely unexpected failure (e.g. ChromaDB corruption, an embedding model issue) that should never leak a raw traceback to an HTTP client. Verified with a mocked `RuntimeError`: response is `500` with the generic message, and the original exception text does not appear anywhere in the response body.
- **`/health` is a bare liveness check**, deliberately not a readiness check — it doesn't verify ChromaDB or `llama-server` connectivity. Matches its stub docstring ("uptime/liveness checks"); a deeper readiness probe could be added later if the deployment setup needs one (e.g. a load balancer health check that should fail if the LLM server is down), but that's a different concept and not needed yet.
- **Verified without touching `app/main.py`**: mounted both routers into a throwaway `FastAPI()` instance with `TestClient` in a scratch script, covering: `GET /health` (200, correct body), `POST /chat` confident case (200, correct grounded answer + email), `POST /chat` fallback case (200, correct fallback fields), request validation (empty-string and missing `question` both correctly `422`, powered by `Field(min_length=1)` — no custom validation code needed), and the mocked-exception 500 case. `app/main.py` (Task 12) will do the real mounting; this only proves the routers themselves are correct in isolation.
- **Real-world confirmation of two previously-known limitations, not new ones**: during this verification run (not a mocked test), one live `/chat` response triggered the Task 10 email-drift warning for real (the model's answer omitted the support email that time) and separately produced another wrong abbreviation expansion ("LDAP (Login Access)", following "LDAP (Library Access)" from Task 9's testing). Both are the same residual 3B-model limitation already documented, now confirmed to recur rather than being one-off flukes. **Update (production-readiness pass)**: this is no longer monitor-only. `rag_pipeline.py` now appends a `"\n\n(Verified contact: {email})"` clause to the answer whenever drift is detected, in addition to still logging the warning — see the new section at the end of this file.

## App assembly (`app/main.py`)

- **Deliberately minimal**: `FastAPI(title=...)` plus `include_router()` for both routers, nothing else. Matches the "stay thin" convention already documented for this file.
- **Considered and deliberately deferred, not forgotten**:
  - *CORS middleware* — will very likely be needed once `frontend/` (Task 13) actually calls `/chat` from a browser on a different origin/port than the API. Not added now because Task 12's documented scope is "wire routers," and adding it speculatively before Task 13 exists risks configuring it against assumptions that turn out wrong (e.g. whether the frontend ends up served by this same FastAPI app via `StaticFiles`, or by a separate dev server). Revisit as part of Task 13 once the actual serving setup is decided.
  - *Startup warmup hook* (pre-loading the embedding model before the first real request) — the embedding model currently lazy-loads on the first call that needs it (by design, see Embeddings section above), which means whichever request triggers that first load pays a multi-second penalty (observed directly multiple times this session). A `lifespan`/startup hook that does one throwaway `embed_query` call at boot would eliminate this for real users. Not added — it's an operational nicety, not part of "wire routers," and better justified once there's an actual deployment target where cold-start latency matters (vs. local dev where it's a one-time non-issue). Worth revisiting before real deployment (Task 15).
- **Verified two ways**: (1) started the real process via the exact documented command (`uvicorn app.main:app`), not just an in-process test client, and hit `/health`, `/chat` (both confident and fallback cases), and a validation-error case, all via real `curl` over the network; (2) fetched `/openapi.json` and confirmed both `/health` and `/chat` are registered — a free correctness check that the schema/router wiring is intact, since FastAPI generates this automatically from the actual app object.

## Frontend (`frontend/index.html`, `frontend/style.css`, `frontend/script.js`)

- **Design direction**: user-chosen — chat bubbles with a "transparency footer," specifically to keep the project's core "never guess silently" principle visible in the UI, not just in the backend logic. Every bot message visually declares its own confidence state rather than presenting all answers identically.
- **Three distinct bot message states**, deliberately not just one generic "bot message" style:
  - **Confident** (`is_confident: true`): neutral light-gray card, plain answer text, plus a small footer row (a green status dot + `"{category} · verified answer"`) — this is the "transparency" element, always visible, not hidden behind a tooltip or debug panel.
  - **Fallback** (`is_confident: false`): a visually distinct warm/amber card (not red — a fallback is a *successful*, correct response, the system correctly declining to guess, not an error) with a clickable `mailto:` link built from `support_email`.
  - **Error** (network failure or non-2xx from `/chat`): a separate red-tinted card, only for genuine request failures. Deliberately kept visually distinct from the fallback state — conflating "the system correctly said it doesn't know" with "the system is broken" would undermine trust in the fallback path.
- **CORS / `API_BASE_URL`, update (production-readiness pass)**: the "serve via `StaticFiles`" option floated below was taken. `app/main.py` now mounts `frontend/` same-origin, `script.js`'s `API_BASE_URL` is `""` (relative), and CORS middleware is conditional on `settings.cors_origins` (empty by default) rather than a hardcoded wildcard. ## Production-readiness pass

Prompted by asking directly "will this work in production" and getting an honest "not yet" — the gaps found were concrete, not speculative, so this pass closed every one that's actually fixable from the repo:

- **Same-origin frontend serving**: `app/main.py` now mounts `frontend/` via `StaticFiles(directory="frontend", html=True)`, mounted *after* both routers so `/health`/`/chat` still take priority over the catch-all. `script.js`'s `API_BASE_URL` is now `""` (relative). This single change closed two blockers at once (see the superseded CORS/`API_BASE_URL` notes above) — one process, one origin, nothing to reconfigure per-deploy.
- **CORS made conditional, not wildcard**: `CORSMiddleware` is only added if `settings.cors_origins` (a new `Settings.cors_origins` property, parsed from comma-separated `CORS_ALLOWED_ORIGINS`) is non-empty. Default is empty — the frontend needs no CORS since it's same-origin; this only matters if some future external consumer calls `/chat` directly.
- **`scripts/reset_db.py` implemented for real**, matching its original docstring. This was prompted by a real bug found while writing a regression test (`tests/test_retriever.py::test_collection_size_matches_source_jsonl_row_count`): the collection had 84 vectors, not 82 — two orphaned entries (`network_rule_1`, `network_rule_2`, the pre-rename ids of what are now `rule_22`/`rule_23`) left behind because `ingest.py` upserts but never deletes. Fixed by hand for the live collection; `reset_db.py` now prevents recurrence by wiping `vectorstore/chroma_db` and rebuilding from `load_knowledge_base()`/`upsert_rules()` (both extracted from `ingest.py` so the two scripts can't drift apart).
- **LLM email-drift now self-corrects** (see the updated RAG pipeline note above) rather than only logging.
- **`docs/deployment.md` written** (previously referenced everywhere, didn't exist) — covers the `llama-server` RUNPATH rebuild requirement (can't be fixed from this repo, only documented as a mandatory first deployment step), systemd unit setup (`deploy/*.service`), and post-deploy verification.
- **CI added** (`.github/workflows/tests.yml`) — installs deps, runs `scripts/ingest.py`, then `pytest`, on every push/PR. This is exactly the safety net that would have caught the Hpce ingest-schema-drift bug (and the orphaned-vector bug above) automatically instead of by hand.
- **Still open, not fixable from the repo**: the real Network support-team mailbox spelling (`helpdesknetwork@` vs `helpdesknetworks@iitm.ac.in`) remains unconfirmed against the actual address — flagged repeatedly now, needs a human with access to the real mailbox to resolve before this is fully production-correct.
